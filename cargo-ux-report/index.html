UX & Purchase Funnel Report

Where CarGo
Loses Customers

Thirty days of behavioral data across 12,600 users in the purchase funnel reveals two structural failures that together collapse conversion to near zero. This report covers the full digital experience — from discovery through booking completion and the host onboarding flow — with session-level evidence for the highest-impact issues.

89.6% hit cart error 69% payment API failure ~1.2% funnel pass-through Fullstory MCP · 30d window
TL;DR

Two walls are shutting down the purchase funnel

Of 12,600 users who entered the purchase funnel, 89.6% hit a hard stop at the car detail page before ever reaching checkout. The "car is not available" error surfaces immediately on every attempt to book specific vehicles — but the inventory system offers no explanation, no alternative cars, and no path forward. Users rage click, then leave.

For the roughly 1.2% who make it through to checkout review, a second wall appears: the /v2/payments/approveFunds endpoint fails for 69% of them. Two of three session recordings show the failure is completely silent — no error state rendered, leaving users clicking a non-responsive submit button until they abandon.

Beyond the purchase funnel, frustration signals appear at every stage: rage clicks on non-interactive elements, city inventory API failures across 10+ markets, a 404 routing issue hitting 19,511 users, and broken UI patterns in checkout navigation.

Wall 1 — Car Availability Failure

🚗

7,113 users blocked (89.6% of funnel)

The inventory system surfaces cars that are not actually bookable. When a user clicks Add to Cart, the API returns an availability error immediately — there's no loading state, no partial success, just an instant failure message.

📍

10+ city markets also returning network errors

The /v2/cars/getAllCarsInOrgInCity endpoint is failing for Oklahoma City, Indianapolis, Charlotte, Austin, New York, Madison, Albuquerque, Savannah, St. Louis, Lansing, and others — 300–357 users per city.

🤷

Zero recovery UX at the failure point

The error gives no reason (date conflict? car condition? already booked?), no alternative car suggestions, no "check back" guidance. Users have nothing to do except leave.

Wall 2 — Payment Processing Failure

💳

69% payment API failure at final confirm

POST /v2/payments/approveFunds fails at the network level for 49 of ~71 users who reach checkout review. This is not a user payment method issue — it's an API reliability problem.

🔇

Silent failures are the norm

Session recordings show that 2 of 3 sampled payment failures produced no visible error state. The submit button appears to do nothing. Users rage click, wait, then abandon — with no idea what went wrong or how to fix it.

🔁

No retry or recovery path offered

Not one recorded session shows a user successfully editing their payment method or retrying with a different card after failure. There is no prompt to do so — the UI offers no guidance after the API fails.

Additional checkout friction: Even among users who don't hit the payment API failure, checkout has structural UX problems — checkout progress step labels (Billing, Payment) look interactive but aren't clickable, rage-clicked by 441–464 users. The Edit Ride and Edit Billing buttons in the review step are also rage-clicked by 289–320 users, suggesting the edit flow is not working reliably.

Section 05

Recommendations

Five prioritized fixes ordered by conversion impact. The first two address structural failures — everything downstream improves only after these are resolved.

P1 · Critical

Fix car availability — filter unbookable inventory from search results

The root cause is that the inventory system surfaces cars that fail the availability check. Either pre-filter results to only show bookable cars, or surface availability status inline on the search card so users never reach the PDP for an unavailable car. This single fix unblocks 89.6% of the purchase funnel. Also investigate and resolve the 10+ city markets returning API errors on /v2/cars/getAllCarsInOrgInCity.

P1 · Critical

Fix /v2/payments/approveFunds reliability and surface errors explicitly

The payment API is failing for 69% of users at the final step. Investigate and resolve the network-level failures. In parallel, ensure every failure path renders an explicit, actionable error state — "Your payment couldn't be processed. Please check your card details or try a different method." Session evidence shows the current implementation silently fails for the majority of users, leaving them with no information and no recovery path.

P2 · High

Add post-availability-error recovery UX on the car detail page

When a car is unavailable, show why (date conflict, already booked, condition) and surface 3–5 similar available vehicles inline. Session recordings show users scrolling back up the listing looking for an explanation — a recovery surface here would recapture a meaningful portion of these abandonments rather than sending them back to a cold search page.

P2 · High

Fix routing and resolve the 404 page refresh loop

19,511 users are landing on the 404 page with an 87% immediate refresh rate — indicating broken inbound links, expired deep links, or a routing regression. Audit inbound link sources, add redirect logic for common broken paths, and improve the 404 page itself with search and navigation options so users who do land there have a recovery path.

P3 · Medium

Fix checkout navigation UX and car image/title click targets

Make checkout progress step labels (Billing, Payment) clickable for backward navigation — 441–464 users are rage clicking these expecting navigation that doesn't exist. Fix the car image and title link click targets on search results — 52% of funnel users rage click these, indicating the navigation from search results to the car detail page has a hit-target or routing problem. Also fix the share button SVG element click interception on the PDP.
