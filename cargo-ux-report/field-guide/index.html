The Core Frame
Lead with this. The structural story matters more than any individual data point.
// PRIMARY ARGUMENT
We have two structural failures shutting down the purchase funnel — one at the top, one at the bottom — and between them, less than 2% of users who try to book actually complete a purchase.

This is not a UX polish issue. These are engineering failures with measurable conversion impact. The car availability error alone blocks 89.6% of users in the purchase funnel before they ever reach checkout. The payment API failure blocks 69% of the survivors. Session recordings confirm that users are trying — they're rage clicking, scrolling for explanations, retrying. The product is failing them, not the other way around.

// THE NUMBERS

Lead with the funnel math — it's damning on its own

  • 12,600 users entered the purchase funnel in 30 days
  • 7,113 (89.6%) hit the cart error on the car detail page
  • ~154 made it to checkout review (~1.2% pass-through)
  • 49 of those hit payment API failure (69%)
  • Effective conversion: well under 1% of funnel entrants
// SESSION EVIDENCE

The sessions tell the human story behind the numbers

  • Every sampled session ended in abandonment — 5 of 5
  • Cart error: users scroll for an explanation that isn't there
  • Payment: 2 of 3 sessions show SILENT failure — no error shown
  • No user attempted a payment method edit after failure
  • No "try similar cars" was offered after availability error
// FULL PICTURE

Beyond the purchase funnel, friction exists at every stage

  • 19,511 users hitting the 404 page (87% refresh rate)
  • 52% of funnel users rage click car titles that don't navigate
  • 40% rage click car images expecting navigation
  • 581 users hitting errors on host-side "Finalize Lineup"
  • 10+ city markets returning inventory API errors
// STOPPER

If leadership asks "why now" or "how bad is it really"

  • This is 30-day data — the failures are ongoing, not historic
  • 89.6% cart error rate is not a long tail edge case — it's structural
  • Silent payment failures mean users don't even know they failed
  • The Fullstory MCP produced this analysis in hours, not weeks — the monitoring capability is now in place to track resolution in real time

Section-by-Section Presenter Notes
Scripted bullets aligned to each section of the full report. Use when walking through the asset with leadership or engineering.
# Section 01 — Full Funnel Overview
// presenter bullets
  • Six stages covered — We mapped every stage from first search through host onboarding. This isn't a partial view.
  • Severity color coding — Red dots are conversion-blocking. Orange are significant drop-off. Purple are UX friction that compounds the others.
  • The cross-cutting column — The 404 issue (19,511 users) is separate from the purchase funnel — it's losing acquisition traffic before users even get started.
  • Pause here for questions on any stage. Leadership will likely want to anchor on the car detail page number — let them, then connect it to Wall 1.
# Section 02 — The Two Walls
// presenter bullets
  • Wall 1 is the bigger fix — 89.6% is not a targeting problem or a messaging problem. It's inventory data quality. Unbookable cars are appearing as available in search results.
  • Wall 2 is the scarier one — Even users who fight through everything still hit a 69% payment API failure at the last click. And most of them don't even see an error message — the UI silently fails.
  • These require different teams — Wall 1 is inventory/search API. Wall 2 is payment infrastructure. Frame them as separate workstreams with separate owners.
  • If engineering is in the room: the payment endpoint is /v2/payments/approveFunds — network-level failures, not HTTP 4xx. This is not a validation issue.
# Section 03 — Session Evidence
// presenter bullets
  • These are real users, not averages — Session recordings are the unvarnished truth. Walk through one cart session and one payment session slowly. The pattern of rage click → scroll → abandon is visceral.
  • The silent failure is the one that lands hardest — Showing a user who clicked submit, got no response, clicked again, waited, and left without knowing their booking failed is more persuasive than any metric.
  • 5 of 5 sampled sessions ended in abandonment — That's not a cherry-picked stat. That's the Fullstory signal group for these failures. There are no green sessions in this cohort.
  • Have the session URLs ready (in Fullstory) in case leadership wants to watch one live. They're in the MCP output from this analysis.
# Section 04 — Priority Matrix
// presenter bullets
  • The critical tier is short — Four issues, two of which are the same root cause (cart availability). This is not a 40-issue backlog. The critical path is narrow.
  • Medium items are real but not the priority — The checkout step label issue (not clickable) and the car image rage clicks matter, but they're downstream of the two walls. Fix the walls first.
  • If product asks about sequencing: P1 items are independent. Both can be worked in parallel by separate teams without coordination cost.
# Section 05 — Recommendations
// presenter bullets
  • P1 fixes are pre-requisite — There's no point optimizing checkout UX if 90% of users can't reach checkout. Land the structural fixes first.
  • P1.b is actually two fixes — Fix the API reliability AND fix the silent failure. Even if the API fails occasionally, users need to know it failed and know what to do next.
  • P2 recovery UX is high leverage — Adding "similar available cars" after the availability error costs relatively little but could recapture a meaningful chunk of the 7,113 blocked users.
  • Close with: "We can re-run this analysis in 30 days to measure the before/after on every metric in the priority matrix."

Discovery Questions
For conversations with engineering, product, and data stakeholders. These open the door to root cause — not attacks, just genuine inquiry.
01
Engineering
What does the Add to Cart flow actually check — is availability determined client-side, at the API call, or does it hit a separate inventory service?
opens: root cause
The cart error fires synchronously with no latency — suggesting either a client-side check against stale data, or a fast-failing availability API. Understanding the architecture tells us whether this is a data freshness problem, a cache invalidation problem, or an API contract mismatch. The fix strategy is completely different for each.
If they say...
"It checks against our inventory service" → Ask: what's the TTL on that data? Is it refreshed between search results rendering and the cart add attempt?
"We cache availability in the search index" → The cache is stale. Cars that appear available in search have already been booked or removed from inventory.
02
Engineering
Is there an alert or on-call trigger for the /v2/payments/approveFunds endpoint failure rate? What does the server-side error log show for those requests?
opens: payment root cause
69% failure rate at the payment step means either the endpoint is misconfigured, a downstream payment processor is unreliable, or there's a bug introduced in a recent deploy. This is high enough to have a P1-level alert — if it doesn't exist, that's a secondary finding. Server-side logs will reveal whether this is timeout, auth failure, or a processor-side rejection.
If they say...
"We have monitoring" → Ask: what's the threshold? 69% failure in a 30-day window should have fired. Either the threshold is too high or the monitoring isn't covering this endpoint.
"We don't have per-endpoint monitoring" → This is a separate, immediate action item: add monitoring to the payment critical path.
03
Product
What's the intended behavior when a car in the search results is no longer available? Is there a spec for what the user should see?
opens: UX gap
Session recordings show users scrolling back up the car listing after the error, looking for an explanation. The current behavior is an error message with no context and no recovery path. If there's no spec for this state, that's the gap. If there is a spec that's not being followed, that's a different conversation.
If they say...
"We show an error message" → Yes, but users don't understand why. The ask is: why is the car unavailable, and what should the user do next?
"We're supposed to show alternatives" → So the spec exists but isn't implemented. That's a clear backlog item with defined requirements.
04
Engineering
The /v2/cars/getAllCarsInOrgInCity endpoint is returning network errors for 10+ cities. Is this a known issue? Are those cities intentionally unsupported or should they be returning results?
opens: inventory coverage
Oklahoma City, Indianapolis, Charlotte, Austin, New York, Madison, Albuquerque, Savannah, St. Louis, Lansing, and others are all failing. This is either a configuration gap (cities with no inventory) or a broader API reliability issue. 300+ users per city are being dead-ended in search.
If they say...
"Those cities have no cars" → They should return an empty result with a message, not a network error. The error is what sends Fullstory signals and leaves users confused.
"Those should work" → Then we have a bug. The endpoint is failing silently and there's no alert on it.
05
Data
What was the deploy history in the last 30–60 days? Did any of these failure signals spike after a specific release?
opens: regression identification
If the cart error rate or payment failure rate spiked after a specific deploy, that's a regression with a clear rollback or hotfix path. The Fullstory data has timestamps — we can correlate failure rate changes to deploy dates with a compare-to-previous window query.
If they say...
"We had a deploy on [date]" → Rerun the discover_groups query with compare_to_previous=true to see delta_pct and confirm if that's when the signal spiked.
"These have always been this way" → Then this is a chronic, unmonitored failure, not a regression. Makes the monitoring gap even more significant.
06
UX / Product
What does the payment confirmation UI show when the API call fails? Is there a defined error state, or does the submit button just stop responding?
opens: silent failure
Two of three sampled sessions show zero visible feedback after payment failure — the button appears to do nothing. This may be a race condition, a missing error boundary, or an error state that's conditionally rendered but never firing. Knowing the intended behavior helps scope the fix.
If they say...
"There's supposed to be an error toast/modal" → It's not rendering. Either the error state logic has a bug or the component isn't receiving the failure signal from the API call.
"We don't have an error state for that" → Then the immediate fix is adding one, even before fixing the underlying API. A visible error message is the highest-leverage UX change possible here.

Stakeholder Pushback Handlers
The four challenges you'll hear in the room when presenting these findings.
We know about the cart error — it's on the backlog. Why are you treating it like a crisis?
// Engineering / Product Lead
// response
The scale changes the conversation. "On the backlog" is a different thing when the failure rate is 89.6% of everyone who tries to book a car. This isn't a long tail — it's blocking the majority of purchase intent in the product. Fullstory quantified what was previously anecdotal: this is the conversion issue, not a conversion issue.
// frame
"89.6% is not a bug — it's the product. Every other conversion optimization we do is irrelevant until this is fixed."
How do we know those session recordings are representative? It's only 5 sessions.
// Engineering / Data Skeptic
// response
The sessions are illustrative, not the primary evidence. The 89.6% cart error rate comes from 7,113 users over 30 days — that's the ConsoleErrorsByText signal across the full purchase funnel cohort. The sessions show what that number looks like from the inside. If you want more sessions, we can pull 50 — the pattern will be the same.
// frame
"The five sessions are a window into 7,113. Pull more if you want — we'll add them to this analysis in minutes."
The payment failure rate sounds high, but some of those are users with bad cards. That's expected.
// Product / Finance
// response
Some portion of "Insufficient Funds" errors (15 users, 24.2%) are legitimate payment declines. But the primary signal is a network-level failure on /v2/payments/approveFunds — not an HTTP 402 or card decline response. A connection failure at the API level is not user error. And two of three sessions showed no error message at all — if it were a legitimate decline, the card processor would return something the app should surface.
// frame
"Bad cards return a 4xx. Network failures return nothing. Our problem is the nothing."
This is a demo environment — we can't assume these numbers represent production behavior.
// Leadership / Stakeholder
// response
That's a valid distinction for some signals (bot traffic, internal testing). But the purchase funnel behavioral patterns are real user intent — 12,600 users in the funnel, rage clicks on Add to Cart, and the payment endpoint failures are all consistent with real attempted bookings. The same Fullstory MCP methodology applies directly to production orgs — we can run the identical query against any instrumented customer environment in minutes.
// frame
"The methodology is the proof of concept. Point us at a production org and we'll reproduce this analysis for a real customer."

Fullstory MCP Investigation Workflow
How this analysis was produced. Reproducible in any Fullstory-instrumented org. Total wall-clock time: under 2 hours including session review.
Prerequisite: Fullstory MCP server configured in Claude Code settings. Tools used: get_pages, get_opportunities, discover_groups, get_managed_funnels, get_sessions_for_opportunity.
01
Baseline org survey
Run get_pages, get_opportunities (30d, no scope), and discover_groups (30d, no scope) in parallel. This gives the full page inventory, pre-ranked AI opportunities, and the top frustration/error groups across all users.
# Run all three in parallel — takes <30s
get_pages(regex="")
get_opportunities(time_range="30d")
discover_groups(relative_time_range="30d", limit=10)
02
Identify managed funnels, scope to purchase path
Call get_managed_funnels to find defined funnels. Identify the purchase funnel, checkout funnel, and search-to-checkout funnel. Then run discover_groups scoped to each funnel to get frustration signals specifically among users in those flows.
# Funnel IDs returned by get_managed_funnels
discover_groups(funnel_id="2BWVg4GQY7Uo", relative_time_range="30d")
discover_groups(funnel_id="ytEwKbV4XEIq", relative_time_range="30d")
discover_groups(funnel_id="MSdxpcaXdnZZ", relative_time_range="30d")
03
Identify the highest-impact signal groups
From the discover_groups output, extract the top signals by user_pct within the funnel. Sort by: ConsoleErrorsByText, NetworkErrorByPath, RageClickByElement, DeadClickByElement, ErrorClickByElement. Note the group_id and metric_id for each top signal — you'll need these to pull sessions.
# Key signals identified from this analysis:
ConsoleErrorsByText | "Error. Can't add to Cart..." | 89.6% funnel
NetworkErrorByPath | /v2/payments/approveFunds | 69% checkout review
RageClickByElement | Car Title Link | 52% funnel
RageClickByElement | Car Image | 40% funnel
04
Pull sessions for the highest-impact groups
Use get_sessions_for_opportunity with the metric_id and group_id from step 3. Pull 5–10 sessions per signal group. Pass each session to the fullstory:session-context subagent for analysis — never call get_session_events directly in the main context.
# For each signal group:
get_sessions_for_opportunity(
  metric_id="ConsoleErrorsByText",
  group_id="Error. Can't add to Cart...",
  relative_time_range="30d",
  limit=5
)
# Then spawn session-context agents in parallel
05
Synthesize and write the report
Combine: (a) funnel cohort signal data from discover_groups, (b) opportunity metadata from get_opportunities, (c) page-scoped signals from discover_groups per page, and (d) session-level behavior from the subagents. Build the priority matrix and recommendations from the combined data. Write to the field-playbooks design system format.
# Output: index.html + field-guide/index.html
# Total time: <2h including all MCP calls + writing
