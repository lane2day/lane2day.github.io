A race condition in Marriott.com's Next.js booking SPA causes a redemptionNotAvailableError to fire before the rewards availability API has resolved. When it strikes, it is unrecoverable: Fullstory session analysis across 23 sessions confirms 100% error rate and 0% booking completion in affected sessions. 46,136 users encountered this in the last 30 days.

⚠ 100% error rate — 23/23 sessions 8.5 avg Rate List visits before abandon Race condition — fixable at source
TL;DR

A timing bug is blocking 46,136 users from redeeming their Bonvoy points — and when it hits, there's no recovery path.

When a Bonvoy member (or guest) selects a hotel from search results and lands on the Rate List Menu, the booking SPA fires a client-side validation check before the rewards availability API response arrives. The error fires twice simultaneously — a signature of two concurrent validation passes — and replaces the entire points interface with an error state from which most users cannot recover.

This isn't a data issue, an authentication issue, or a property configuration issue. It affects Guests and Platinum Premier Lifetime Elite members equally, across 10 loyalty tiers, on every platform, in every locale studied. The bug is in the timing of the validation layer relative to the async API call.

46,136 users encountered this in the last 30 days. Zero of the 23 sessions studied resulted in a points booking. Segment analysis of the full 30-day cohort reveals the real cost: the bug does not drive users away — it strips them of their redemption. An estimated 94% of affected users still complete a booking, but all confirmed instances are cash. The points path is completely unrecoverable. Only ~6% abandon without booking anything at all — with one user visiting the Rate List page 37 times before giving up.

02 — Root Cause

A race condition, not a data problem

The booking SPA runs client-side validation on page mount — before the async rewards availability API has had time to respond. This is the core defect. Authentication status, loyalty tier, travel dates, and property configuration are all irrelevant to whether the error fires.

Definitive signal: The console error fires exactly twice simultaneously in every affected session — a signature of two concurrent validation passes executing in parallel. If the error were data-driven (e.g., rewards actually not available), it would fire once, and it would vary by property and date. It doesn't.

The race is only lost when API latency exceeds the validation window, which varies by property and time-of-day.

05 — Behavioral Impact

Frustration loops, not recoveries

When the error fires, users do not understand that they're stuck. They repeat the same action — visiting Rate List Menu, hitting the same error — in an attempt to recover. The experience produces the classic dead-end frustration pattern Fullstory captures as repeated navigation with zero conversion.

07 — Recommendations

Three actions, prioritized by severity

The root cause is addressable with a targeted fix to the validation timing. Two supporting changes — exposing the existing escape hatch and resolving the secondary Select error — would materially reduce harm for users already in the error state while the primary fix is developed and deployed.

Recommended Actions

These recommendations are sequenced by severity and independence. Fix 1 is the systemic repair. Fixes 2 and 3 are mitigations that can ship independently and faster.

Critical

Fix the race condition — gate validation on API resolution

The client-side validation executing redemptionNotAvailableError must not run until the rewards availability API response is confirmed. Options: (a) move validation into the API response callback, (b) add a loading/pending state that defers the validation pass, (c) check for presence of rewards data before executing the validation path. The simultaneous ×2 fire pattern suggests the validation is being triggered by component re-renders in parallel — worth auditing the React effect dependencies for the validation hook.

High

Surface the existing "View Rates" escape hatch

The #RedemptionError element already contains a "View Rates" button that navigates to reviewDetails.mi. Only 1/23 users discovered it. A simple styling change — larger button, higher contrast, explicit label "Continue to rates" — would allow a meaningful percentage of affected users to recover without waiting for the primary fix. This can ship as a CSS-only change.

Medium

Resolve the ReferenceError: Can't find variable: s

This error fires when users attempt to click "Select" on a rate, including after they have navigated away from an errored property to a clean one. The variable s is referenced but undefined in scope at click-time — likely a scoping or initialization issue with an analytics or tracking library (the single-letter variable name is consistent with a minified analytics SDK). This blocks users who have already partially recovered from the redemption error. Resolving it would give persistent users a real path to completion.
