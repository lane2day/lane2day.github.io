Delivery Script

How to walk this report

Follow these steps in order. The report is structured to build from scale → mechanism → evidence → who → impact → action. Don't skip to recommendations before establishing credibility with the data.

Numbered Delivery Steps

1

Open with the headline number, not the bug

Start with 46,136 users and 51,159 sessions in the last 30 days. This grounds the conversation in scale before you explain mechanism.

"Before we get into what's happening, let me show you how many people are affected. In the last 30 days alone, 46,136 unique users hit this — that's the number of users who made it to your Rate List Menu and saw the redemption error before they could complete a booking."

2

Introduce the segment as expert-validated, not generated

Jennifer will want to know this is credible, not a Claude hallucination. Lead with the fact that it was built by a Fullstory expert specifically for this inquiry.

"This segment was built by one of our internal Fullstory experts — not auto-generated. It captures users who visited your search results page and then encountered the RedemptionError element in order, within the same session. That sequence is precise and confirmed."

3

Walk the execution timeline — the race condition visual

The timeline diagram in the deliverable is the key explainer. Walk through it step by step. The ×2 simultaneous fire is the most compelling technical signal — don't rush past it.

"Here's what we see in every affected session: the validation fires twice, simultaneously, within milliseconds of page load — before your rewards availability API has had time to respond. When the API does respond — 200 to 800 milliseconds later — the UI is already locked in the error state. The data says rewards are available. The UI never processes that response."

4

Establish auth-agnostic impact — dispel the tier hypothesis

Jennifer may initially assume this affects non-members or lower tiers. Address it directly with the tier table. The "Platinum Lifetime Elite, 37 RLM visits" example is your most memorable data point.

"Every loyalty tier is affected — from guests to your Platinum Premier Lifetime Elite members. In fact, your most loyal members show the longest frustration loops — they're more determined to use their points, so they keep trying. We observed one Platinum Lifetime Elite member in Rancho Cordova visit the Rate List page 37 times in a single session before giving up."

5

Present behavioral outcomes — the bug strips redemption, not bookings

The cohort data reframes the story. 23-session review showed 87% apparent abandonment (small sample, recency bias). Full 30-day cohort analysis via segment reveals: ~94% of affected users still complete a booking — but all confirmed instances are cash (bookedCurrencyCode = USD or local fiat in every reviewed confirmation session). Only ~6% abandoned without booking anything. Zero sessions resulted in a points booking.

"Here's what makes this finding different: your users don't walk away. About 94% of the 46,136 affected users still complete a booking. But they book with cash — because the 'View Rates' button inside the error state lets them pivot to standard rates. The bug doesn't cost you a reservation. It costs your most loyal members their points. Every one of these 46,136 bookings that should have been redeemed on Bonvoy points ended up as a cash charge instead. That's the loyalty damage."

If challenged on the 23-session vs. cohort discrepancy: The 23-session review captured the most recent sessions — many were still mid-session at time of review. The 30-day cohort segment shows how sessions actually resolved. Both are valid; the cohort data is more representative of population-level behavior.

6

Walk the recommendations in priority order

Present Fix 1 (race condition) as the systemic solution, then emphasize that Fixes 2 and 3 are independent quick wins that can ship while Fix 1 is in development.

"The real fix is gating the validation on the API response — but that's a code change that needs engineering. While that's in flight, there are two things you can do quickly: surface the 'View Rates' escape button that's already in the error UI — just make it more visible — and resolve the secondary variable reference error that blocks users who switch hotels. Neither of those requires touching the validation logic."

7

Leave the session link open as an offer

You have the Fullstory org access and the segment. Offer to pull up a live session replay if Jennifer's team wants to see a specific tier or behavior pattern.

"We have the full session data for all 23 reviewed sessions — and the segment captures every affected user in the last 30 days. If it's useful, I can pull up specific sessions for your engineering team to see the exact error sequence, or filter to a specific tier or platform."

Technical Detail

Engineering-level evidence

Use this section if Jennifer's engineering team joins the call or asks technical follow-up. These are the exact signals from session event data that support the race condition hypothesis.

Key technical signal: The console error fires ×2 simultaneously in every affected session. Simultaneous dual-fire is the definitive signature of two concurrent React effect executions — the validation hook is being triggered by multiple parallel state updates on mount, before the async data has resolved.
Console error format (as captured in Fullstory session events):
// Fires twice simultaneously (within the same requestAnimationFrame window): Client Side Validation Error, Page State: {"pageLevelErrors":{"redemptionNotAvailableE... // Fullstory log truncates at ~80 chars; full key = "redemptionNotAvailableError"
// Timing: fires within ~5ms of page mount, before rewards API response arrives (200–800ms latency) // Pattern consistent across: all browsers, all OS, all tiers, all locales, all properties
React hydration errors also present: 7/23 sessions also showed React hydration errors #418 and #423 on the same page mount. These server/client state mismatches likely contribute to the parallel effect execution pattern — when the hydrated state doesn't match, React re-triggers effects to reconcile, which can produce the dual-fire.
Secondary error — variable 's' undefined: In 11/23 sessions (48%), ReferenceError: Can't find variable: s fires when users click "Select" on a rate card. The single-letter variable name is strongly suggestive of a minified analytics or tracking library (Adobe Analytics uses single-letter variable names extensively in its minified build). This fires even on hotels that did not trigger the redemption error — it's an independent defect in the rate selection path.
Property-specificity mechanism: In sessions where a user checked multiple hotels, 2-5 of 7 hotels triggered the error while others did not. This is consistent with API latency variation — not property configuration. Hotels with faster cached responses resolve before the validation window; hotels with slower responses (higher inventory complexity, uncached availability, geographic latency) lose the race. The same hotel checked on different dates consistently fails (tested in the London session: 5 consecutive date searches, same hotel, all errored) — confirming it is not date-specific but property-latency-specific.

Q&A Prep

Likely questions and answers

Why does it only happen on some hotels and not others?
It's a race condition — it depends on how fast your rewards availability API responds for a given property. Hotels with faster cached responses resolve before the validation fires; hotels with slower responses lose the race. The same user, same session, same browser can see errors on 2 hotels and no errors on 5 others. The London session showed the same hotel failing on 5 consecutive date searches — it's property-latency, not date-specific.
Is this only affecting non-members or low-tier members?
No. We confirmed errors on every tier from Guest through Platinum Premier Lifetime Elite. Authentication and loyalty status are irrelevant to whether the validation fires — it runs before any user-specific data loads. Your highest-tier members actually show the longest frustration loops, likely because they are most motivated to use their points.
Could this be a browser caching issue or a client-side config problem?
No. The error is confirmed across iOS Safari, Android Chrome, macOS Chrome, macOS Safari, Windows Chrome, Windows Edge, and Linux Chrome. Browser-specific or cache-specific issues don't produce this consistent cross-platform pattern. The dual simultaneous console fire is the definitive evidence — this is a code execution sequence problem, not a data or cache problem.
How confident are you in the 46,136 user number?
High confidence in the direction; treat it as a floor, not a ceiling. The segment captures users who (1) visited SERP, (2) had the #RedemptionError element tracked by Fullstory, and (3) these happened in sequence in the same session. Users who abandoned at SERP or whose sessions had partial tracking are not counted. The true affected population is likely larger.
Is this a regression? When did it start?
The 30-day segment window covers our evidence base but we haven't characterized when the bug was introduced. The segment was built within the last 30 days. I can pull a longer time window or a trend view from Fullstory to help establish whether this is new or has been present longer — I'd need to run that separately.
Why does the error fire twice?
Two concurrent React effect executions are running the validation simultaneously on page mount. This is consistent with a React hook whose dependency array includes multiple values that update simultaneously during hydration — causing the effect to fire multiple times in parallel before the async data resolves. The React hydration errors #418 and #423 also present in the same sessions support this — the server/client state mismatch triggers additional effect re-executions.
What's the "View Rates" button you mentioned?
The #RedemptionError element in your DOM already contains a "View Rates" button that bypasses the error state and navigates to reviewDetails.mi. It exists — it just isn't visible or prominent enough for most users to find. Only 1 of the 23 sessions we reviewed had a user who discovered and used it. Making it more prominent (larger, higher contrast, explicit label) could let a meaningful percentage of affected users recover without waiting for the primary fix. This could ship as a CSS-only change.
